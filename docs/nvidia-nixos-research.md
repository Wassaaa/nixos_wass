# NVIDIA on NixOS

Research checked 30 October 2026 for `wassaa` with an RTX 2080, Hyprland, and Brave. Actual NixOS evaluation and playback have not been tested.

## Existing configuration

- The [NVIDIA module](../modules/drivers/nvidia-drivers.nix) already enables modesetting and uses the kernel-matched stable driver. [wassaa](../hosts/wassaa/default.nix) selects NVIDIA's open kernel modules; NVIDIA supports Turing GPUs including the RTX 2080. The userspace driver remains proprietary. [NVIDIA documentation](https://download.nvidia.com/XFree86/Linux-x86_64/595.112.07/README/kernel_open.html)
- The [locked NixOS NVIDIA module](https://github.com/NixOS/nixpkgs/blob/31ecbaca1bdefa45dffc409f0250bd8039ea0010/nixos/modules/hardware/video/nvidia.nix) enables `hardware.nvidia.videoAcceleration` by default and adds `nvidia-vaapi-driver` to `hardware.graphics.extraPackages`. It also configures DRM modesetting and, on this driver generation, fbdev.
- The [locked VA-API package](https://github.com/NixOS/nixpkgs/blob/31ecbaca1bdefa45dffc409f0250bd8039ea0010/pkgs/development/libraries/nvidia-vaapi-driver/default.nix) is version 0.0.18. Its [release notes](https://github.com/elFarto/nvidia-vaapi-driver/releases/tag/v0.0.18) describe a Chromium-compatible decode path.

## Published configurations

- [nixos-hardware's Turing profile](https://github.com/NixOS/nixos-hardware/blob/master/common/gpu/nvidia/turing/default.nix) selects open modules where supported.
- [ZaneyOS's NVIDIA module](https://gitlab.com/Zaney/zaneyos/-/blob/main/modules/drivers/nvidia-drivers.nix) uses a similar stable-driver and modesetting baseline.
- [LinuxBeginnings NixOS-Hyprland](https://github.com/LinuxBeginnings/NixOS-Hyprland/blob/main/modules/nvidia-drivers.nix) enables graphics and modesetting and explicitly adds the VA-API bridge. Explicitly adding it is redundant with this checkout's locked NixOS module.
- [ryan4yin's NVIDIA desktop configuration](https://github.com/ryan4yin/nix-config/blob/main/hosts/idols-ai/hardware-nvidia.nix) also uses open modules, modesetting, and a production driver. It targets different hardware, so its additional settings are not automatically relevant to `wassaa`.

## Brave experiment

[The wassaa configuration](../hosts/wassaa/default.nix) selects the NVIDIA VA-API driver and its direct backend system-wide. The system-wide-only experiment still used software H.264 decoding in Brave. [Brave's configuration](../modules/home/features/desktop/brave.nix) now enables Chromium's experimental `VaapiOnNvidiaGPUs` feature on `wassaa`, preserving the existing acceleration and color-management settings. It does not disable sandboxing or bypass the GPU blocklist. Actual hardware decoding with this opt-in remains unverified.

The [driver's versioned instructions](https://github.com/elFarto/nvidia-vaapi-driver/blob/v0.0.18/README.md#chrome) describe a Chromium-compatible path, but [Chromium](https://chromium.googlesource.com/chromium/src/+/156.0.8078.48/docs/gpu/vaapi.md) still treats NVIDIA VA-API as experimental. The direct backend uses an unstable NVIDIA interface and can regress after driver updates. The bridge only decodes video; it does not provide encoding.

After deploying, quit Brave completely, reopen it, and play a known H.264 video. In `brave://media-internals`, check the selected video's decoder and platform-decoder status. `brave://gpu` can show supported capabilities but does not prove a particular stream is hardware decoded. The RTX 2080 does not support AV1 hardware decoding, so AV1 fallback alone is not evidence that H.264 decoding failed. [NVIDIA codec capabilities](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvdec-video-decoder-api-prog-guide/index.html#video-decoder-capabilities)

## Chromium 156 decode investigation

- **The skip message:** In [Chromium 156.0.8078.79's DRM selection code](https://github.com/chromium/chromium/blob/156.0.8078.79/media/gpu/vaapi/vaapi_wrapper.cc), `Should skip nVidia device named: nvidia-drm` means a node was marked to be skipped because `VaapiOnNvidiaGPUs` was disabled. The [feature is disabled by default](https://github.com/chromium/chromium/blob/156.0.8078.79/media/base/media_switches.cc). This explains the observed Chrome log without an opt-in, but does not prove why every profile is blank. The explicit `--hardware-video-device-path` override is an exception to the skip, not a recommended workaround.
- **Opt-in is only one gate:** The existing system-wide `LIBVA_DRIVER_NAME=nvidia` and `NVD_BACKEND=direct` select the bridge and backend; they do not enable Chromium's feature. The host-specific Brave opt-in removes this particular gate, but driver loading, VA initialization, codec support, device access, and actual frame presentation still matter. [Chromium's Linux VA-API documentation](https://chromium.googlesource.com/chromium/src/+/156.0.8078.79/docs/gpu/vaapi.md#VaAPI-on-Linux) calls the path unsupported and the NVIDIA feature a developer test, with no guarantees. Its build instructions also require proprietary-codec support for H.264 in a Chromium build.
- **Driver and sandbox:** [Version 0.0.18](https://github.com/elFarto/nvidia-vaapi-driver/releases/tag/v0.0.18) added a Chromium direct-backend path; the [driver README](https://github.com/elFarto/nvidia-vaapi-driver/blob/v0.0.18/README.md#configuration) requires DRM modesetting and says EGL is broken on NVIDIA 525+, while direct uses an unstable NVIDIA interface. The [direct backend](https://github.com/elFarto/nvidia-vaapi-driver/blob/v0.0.18/src/direct/nv-driver.c) opens NVIDIA device nodes and uses ioctls, so permissions and sandbox confinement can matter even if a DRM node was opened. The [driver's `NVD_FORCE_INIT` check](https://github.com/elFarto/nvidia-vaapi-driver/blob/v0.0.18/src/vabackend.c) overrides its sandbox-detection heuristic, not device permissions. Do not assume disabling the GPU sandbox, using `--no-sandbox`, or bypassing the blocklist is necessary: these weaken protections or bypass checks, and none establishes working playback. Firefox's `MOZ_DISABLE_RDD_SANDBOX` is not a Chromium setting.
- **Reported failures, not predictions for this machine:** [Issue #474](https://github.com/elFarto/nvidia-vaapi-driver/issues/474) reports a GPU-process crash on a 284x160 H.264 video with v0.0.18 direct, Brave/Chromium 154, NVIDIA 610, and an RTX 5070 Ti; the reporter says browser-local `NVD_SINGLE_BUFFER=1` avoided that case. The tagged README's claim that single-buffer export is always used conflicts with [the v0.0.18 implementation](https://github.com/elFarto/nvidia-vaapi-driver/blob/v0.0.18/src/direct/direct-export-buf.c); [initialization](https://github.com/elFarto/nvidia-vaapi-driver/blob/v0.0.18/src/vabackend.c) checks whether the variable exists, so even `0` enables it. It is not a general fix: [issue #464](https://github.com/elFarto/nvidia-vaapi-driver/issues/464) reports CUDA 999 and failed surface imports after decoder recreation with v0.0.18, NVIDIA 615, and an RTX 4060 laptop; one separate report says single-buffer did not fix that failure. Neither report establishes a failure on NVIDIA 595, RTX 2080, or Chromium 156.
- **Practical comparison:** [NVIDIA's Turing capability table](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvdec-video-decoder-api-prog-guide/index.html#video-decoder-capabilities) lists H.264 Baseline/Main/High through level 5.1, but not AV1. Test the same known H.264 stream and resolution in each browser: `FFmpegVideoDecoder` indicates the observed software path, while Chromium documents `GpuVideoDecoder` in `chrome://media-internals` as the accelerated-path check; use `brave://media-internals` for Brave. A successful `vainfo` or nonempty `chrome://gpu` profiles alone does not prove a particular stream uses hardware. Hardware decode can reduce CPU work, but GPU/CUDA power and presentation overhead may offset savings; compare CPU load, dropped frames, stability, and whole-system power for the same workload. Software decode remains a reasonable baseline when smooth and avoids relying on this experimental bridge. [Chromium verification guidance](https://chromium.googlesource.com/chromium/src/+/156.0.8078.79/docs/gpu/vaapi.md#Verifying-VaAPI-installation-and-usage), [NVIDIA NVDEC overview](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvdec-video-decoder-api-prog-guide/index.html#overview)
