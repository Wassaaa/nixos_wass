# Brave on Wayland and Hyprland

Research checked 30 October 2026. Runtime behavior and installed versions on the NixOS hosts were not tested.

## Current configuration

- [Hyprland](../modules/home/features/desktop/hyprland/hyprland.nix) sets `NIXOS_OZONE_WL=1` and enables XWayland. The environment variable alone does not establish which backend a running window uses.
- [Brave](../modules/home/features/desktop/brave.nix) no longer disables `WaylandWpColorManagerV1`, a former workaround for a [multi-monitor crash](https://github.com/brave/brave-browser/issues/49921). Brave closed that issue after merging Chromium 142.0.7444.53; users confirmed the fix in Brave 1.84.130 without the workaround. Behavior without the flag on this configuration remains unverified.
- The [portal configuration](../modules/core/features/desktop/portals.nix) selects Hyprland and GTK backends for Hyprland sessions. Portal availability does not prove that screen sharing works.

## Reported issues

- An [open report](https://github.com/brave/brave-browser/issues/57885) describes black AV1 video on NVIDIA and Wayland with graphics acceleration enabled; another report includes Hyprland. The original reporter found software decoding succeeded but frames were not presented. This is not evidence that all NVIDIA or Hyprland setups are affected.
- An [open report](https://github.com/brave/brave-browser/issues/60257) describes one Brave 1.98.60 process consuming a CPU core on Hyprland. The reporter had no reliable reproduction and had not compared a clean profile or XWayland.
- An [open report](https://github.com/brave/brave-browser/issues/59781) describes software video decoding on an AMD/Sway setup despite the GPU page reporting acceleration. It is not a Hyprland-specific finding.
- An [open report](https://github.com/brave/brave-browser/issues/51651) describes a screen-capture portal failure on one Hyprland/OpenRC setup; it does not establish a general Brave defect.

## Checks

1. In `brave://version`, record the Brave and Chromium versions and command line. Quit Brave completely before comparing launch arguments because a new invocation can reuse the existing browser process.
2. Inspect Brave's window in `hyprctl clients`: `xwayland: 0` means native Wayland and `xwayland: 1` means XWayland. `brave://gpu` may also show `Ozone platform: wayland`. The session type and browser user-agent string do not prove the window backend. [Chromium Ozone](https://chromium.googlesource.com/chromium/src/+/main/docs/ozone_overview.md)
3. Check `brave://gpu` for hardware-accelerated compositing and WebGL, the renderer, and problems or logs. SwiftShader or llvmpipe indicates software rendering for the relevant path; disabled Vulkan alone does not mean GPU acceleration is broken. [Chromium GPU debugging](https://chromium.googlesource.com/chromium/src/+/main/docs/gpu/debugging_gpu_related_code.md)
4. While a video plays, inspect its player in `brave://media-internals` for codec, decoder and platform-decoder status. `VaapiVideoDecoder` indicates VA-API selection; decoder names can vary. GPU capabilities or `vainfo` alone do not prove hardware decoding of the current video. Test relevant codecs independently. [Chromium VA-API](https://chromium.googlesource.com/chromium/src/+/main/docs/gpu/vaapi.md)
5. Test actual window and screen capture with the [WebRTC display-capture sample](https://webrtc.github.io/samples/src/content/getusermedia/getdisplaymedia/), then test the meeting application and verify received video. Check application audio and microphone separately. [ScreenCast portal API](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.ScreenCast.html)

Avoid adding large flag bundles or disabling GPU acceleration or sandboxing without a specific problem and a controlled comparison. Review diagnostic output for sensitive URLs and paths before sharing it.

## Color management: upstream evidence

- Chromium's [original implementation](https://chromium-review.googlesource.com/c/chromium/src/+/6771393) enables `WaylandWpColorManagerV1` by default to use the Wayland color-management protocol, including HDR surfaces on supported platforms. Its [color-manager code](https://chromium.googlesource.com/chromium/src/+/main/ui/ozone/platform/wayland/host/wayland_wp_color_manager.cc) exchanges surface and output color descriptions and HDR metadata; this is also relevant to SDR colors, not just HDR. Compositor support and capabilities matter; Chromium's current [image-description code](https://chromium.googlesource.com/chromium/src/+/main/ui/ozone/platform/wayland/host/wayland_wp_image_description.cc) does not implement ICC-file handling. Current mainline source is not proof of the exact implementation in the installed Brave build.
- [Brave #49921](https://github.com/brave/brave-browser/issues/49921), now closed, reported Brave 1.83.109 / Chromium 141 crashing when a native-Wayland window crossed monitors, including on Hyprland; its log contained an `invalid object` error. XWayland and disabling this feature were reported workarounds. The [Chromium fix](https://chromium-review.googlesource.com/c/chromium/src/+/7003036) destroys the old preferred image-description object before requesting a replacement; [Hyprland also merged a compositor-side fix](https://github.com/hyprwm/Hyprland/pull/11877). Brave stated Chromium 142.0.7444.45 or later was needed, merged 142.0.7444.53 into 1.84.x and 1.85.x, and affected users confirmed Brave 1.84.130 worked without the flag. This fixes that specific crash, not every color, multi-monitor, or NVIDIA problem.
- For the reported Brave 1.98.60 / Chromium 156, the original crash fix is already well behind the installed version. A controlled test without the disable flag is reasonable, not a guarantee of correct colors or stability. Removing the flag permits the default color-manager path only when the compositor exposes a compatible protocol; it may change SDR color or per-monitor behavior, and may allow HDR where the whole stack supports it. Keeping the flag avoids that path but users report losing in-browser HDR; neither choice establishes that the RTX 2080, driver 595, two displays, and this Hyprland session will work correctly. [Chromium implementation](https://chromium-review.googlesource.com/c/chromium/src/+/6771393) | [Hyprland HDR discussion](https://github.com/hyprwm/Hyprland/discussions/14999)
- Separate issues remain: [Brave #50027](https://github.com/brave/brave-browser/issues/50027) is open for washed-out colors, including SDR reports; its recent Chrome 155/KWin trace suggests a timing issue but does not prove its cause. Chromium changes [8294700](https://chromium-review.googlesource.com/c/chromium/src/+/8294700) and [8295199](https://chromium-review.googlesource.com/c/chromium/src/+/8295199) are unmerged work in progress, not established fixes for this system. On HDR outputs, [Hyprland #16329](https://github.com/hyprwm/Hyprland/issues/16329) remains open for configurable reference luminance; [a separate NVIDIA 590 report](https://github.com/hyprwm/Hyprland/issues/13417) describes dim SDR browser content on HDR and was closed by a bot, not marked fixed. An [unanswered Hyprland 0.57.0 discussion](https://github.com/hyprwm/Hyprland/discussions/16720) reports a black/frozen HDR-capable NVIDIA output with another display unaffected; it is not evidence of a Brave color-manager fault.

## Pinned packaging and practical baseline

- The root [lock file](../flake.lock) pins nixpkgs `31ecbaca1bdefa45dffc409f0250bd8039ea0010`; its [Brave package metadata](https://github.com/NixOS/nixpkgs/blob/31ecbaca1bdefa45dffc409f0250bd8039ea0010/pkgs/applications/networking/browsers/brave/packages/brave.nix) says 1.98.60. The active NixOS generation and running browser can differ from this checkout.
- At that pin, the [Brave wrapper](https://github.com/NixOS/nixpkgs/blob/31ecbaca1bdefa45dffc409f0250bd8039ea0010/pkgs/applications/networking/browsers/brave/make-brave.nix) defaults to libva/video-acceleration support and adds `AcceleratedVideoDecodeLinuxGL` and `AcceleratedVideoEncoder`, plus disables `OutdatedBuildDetector` and `UseChromeOSDirectVideoDecoder`; Vulkan is not enabled by default. These are package defaults, not proof hardware decoding works or that the local experiment is still applied. The pinned [Home Manager module](https://github.com/nix-community/home-manager/blob/095fef2f265c3c0da4fe315efba8f8a04495ab34/modules/programs/chromium.nix) passes nonempty `programs.brave.commandLineArgs` through the package override. Both wrapper and customization can emit `--disable-features`; do not assume duplicated switches merge: Chromium's [command-line code](https://chromium.googlesource.com/chromium/src/+/156.0.8078.47/base/command_line.cc) normally replaces a duplicate value unless a handler intervenes. Inspect the actual command line and effective behavior; wrapper ordering and downstream overrides need runtime confirmation.
- When both `NIXOS_OZONE_WL` and `WAYLAND_DISPLAY` are nonempty, that wrapper adds `--ozone-platform-hint=auto`, `WaylandWindowDecorations`, and `--enable-wayland-ime=true`; it does not explicitly force `--ozone-platform=wayland`. An explicit [Ozone platform](https://chromium.googlesource.com/chromium/src/+/main/docs/ozone_overview.md) is useful for a targeted native-Wayland versus XWayland comparison, but first verify the actual window backend. Do not copy obsolete flag recipes or presume that Chrome, Chromium, and Brave use identical distro wrappers.
- The system [Hyprland module](../modules/core/features/desktop/de-hyprland.nix) supplies the matching flake portal; Home Manager sets `portalPackage = null` to avoid supplying another. [Portal selection](../modules/core/features/desktop/portals.nix) prefers Hyprland then GTK and exports session variables via the [Hyprland configuration](../modules/home/features/desktop/hyprland/hyprland.nix). The [portal specification](https://flatpak.github.io/xdg-desktop-portal/docs/portals.conf.html) selects backends using `XDG_CURRENT_DESKTOP`; verify the live session, portal services, PipeWire, picker, and received frames if capture fails. [Hyprland's portal project](https://github.com/hyprwm/xdg-desktop-portal-hyprland) recommends using the portal from the Hyprland flake.
- Prefer normal GPU acceleration and a small, issue-specific configuration; test WebGL, compositing, each video codec, and screen sharing independently. Chromium's [VA-API documentation](https://chromium.googlesource.com/chromium/src/+/main/docs/gpu/vaapi.md) calls Linux VA-API unsupported and NVIDIA VA-API a developer testing path with no guarantees. The reported experiment produced a 284x160 decoder error followed by fallback and reported WebGL off; neither proves a root cause or that decoding, WebGL, and color management failed for the same reason. Do not add blocklist bypasses, sandbox changes, or experimental video flags as a general fix.
- For a color-manager comparison, fully quit Brave, keep the same browser build, profile, backend, displays and GPU settings, and compare the former flag against a launch where it is genuinely absent, checking `brave://version` and any other launch sources. On each display and while moving between them, check SDR colors and stability; test HDR separately only if configured and supported. Recheck `brave://gpu` and the same playing video in `brave://media-internals`, and test screen capture separately. An isolated profile can help rule out profile effects but does not by itself bypass a packaged wrapper. The rollback remains unverified until deployed and tested by the user.
