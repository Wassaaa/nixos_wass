## What upstream policy actually provides

- **Defaults and history.** WirePlumber normally chooses the highest `priority.session` only in the absence of a user-configured default. `node.restore-default-targets` defaults to true and stores manual defaults and their history; turning it off stops restoration, but still honors runtime choices. Therefore a high virtual priority alone does not reliably override a remembered physical default, and selecting a physical default in an ordinary volume UI changes the global default rather than an independent backing-device preference. [Settings](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/settings.html), [priorities](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/priorities.html), [0.5.18 selected-default hook](https://github.com/PipeWire/wireplumber/blob/0.5.18/src/scripts/default-nodes/find-selected-default-node.lua).
- **Candidate ranking is not history.** The 0.5.18 default rescan considers sinks and duplex nodes for playback, and sources, virtual sources, duplex nodes and sinks for capture, provided they have suitable ports and available device routes. Automatic best-default selection excludes sink monitors as sources and smart filters. The ranking compares session priority, route priority within a device, then object age; the separate best-stream-target fallback breaks equal priorities by most recently plugged linkable. Neither ranking defines the previously chosen physical default. [Candidate collection](https://github.com/PipeWire/wireplumber/blob/0.5.18/src/scripts/default-nodes/rescan.lua), [best default](https://github.com/PipeWire/wireplumber/blob/0.5.18/src/scripts/default-nodes/find-best-default-node.lua), [ranking](https://github.com/PipeWire/wireplumber/blob/0.5.18/src/scripts/lib/node-utils.lua), [best stream target](https://github.com/PipeWire/wireplumber/blob/0.5.18/src/scripts/linking/find-best-target.lua).
- **Stream targeting and changes.** An untargeted stream uses the global default, then the best available target, so setting a proxy as global default does not reveal a separate physical default to its backing stream. `target.object` on the *stream* names a node or object serial; `target.object` in `default` metadata can move that stream dynamically when moving is enabled and `node.dont-move` permits it. Object serials are runtime identities; stable, unique `node.name` values are preferable for persistent preferences, subject to device/profile changes. A client stream initially targeting the current default may follow later default changes; the documented `linking.follow-default-target` exception does not apply to filter streams. [Linking policy](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html), [settings](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/settings.html), [0.5.18 target hook](https://github.com/PipeWire/wireplumber/blob/0.5.18/src/scripts/linking/find-defined-target.lua), [PipeWire properties](https://pipewire.pages.freedesktop.org/pipewire/page_man_pipewire-props_7.html).
- **Missing targets and hotplug.** By default an unavailable explicit target can fall back to the default or best target, and streams normally attempt reconnection after removal. `node.dont-fallback = true` prevents fallback but destroys the stream and reports an error when the target is missing; combining it with `node.linger = true` leaves the stream waiting instead. These are stream properties, not device properties. Linkable and route changes trigger policy rescans, but seamless recovery, switching to a new preferred device and application survival require testing. [Linking policy](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html), [0.5.18 default rescans](https://github.com/PipeWire/wireplumber/blob/0.5.18/src/scripts/default-nodes/rescan.lua), [linking rescans](https://github.com/PipeWire/wireplumber/blob/0.5.18/src/scripts/linking/rescan-on-linkable.lua).
- **Smart filters are not a second default.** They insert paired, same-`node.link-group` processing nodes transparently in front of a target; single-node null sinks are not smart filters. Without `filter.smart.target`, they follow the global default. A target is a property match, and the 0.5.18 implementation finds a matching node rather than ranking physical devices or restoring a separate choice. Updating `filter.smart.target` in `filters` metadata triggers filter relinking. Automatic best-default selection excludes smart filters, so do not assume a smart filter will also become the visible default. [Smart-filter documentation](https://pipewire.pages.freedesktop.org/wireplumber/policies/smart_filters.html), [0.5.18 filter implementation](https://github.com/PipeWire/wireplumber/blob/0.5.18/src/scripts/lib/filter-utils.lua).

## Design options (proposals, not verified implementations)

Use distinct visible virtual endpoints and independent backing streams: application playback -> Main Audio -> selected physical sink; selected physical source -> Microphone Proxy -> capture applications. PipeWire's [loopback module](https://pipewire.pages.freedesktop.org/pipewire/page_module_loopback.html) documents virtual sinks and sources and separately configurable capture/playback sides. The existing null source could instead receive a managed source-to-sink link, but this needs graph testing. A virtual node alone is not an active physical link.

1. **External selector:** maintain separate user-selected physical input/output preferences, enumerate only appropriate available physical candidates, rank the rest when no saved eligible choice exists, and retarget each backing stream via `default` metadata. Watch additions, removals, routes, profile changes and metadata; wait or select an explicitly approved fallback when missing. Define behavior for a preferred device returning, prevent stale IDs and ownership races, and handle daemon restart. A separate control is needed for physical choice while system defaults stay virtual. This offers explicit UX and persistence but introduces a service, state and synchronization.
2. **WirePlumber Lua policy:** a custom hook could select targets specifically for the backing streams and maintain independent preferences, using graph events and appropriate rescan/relink triggers. It integrates with policy but has version-sensitive APIs, ordering and persistence complexity; merely adding a hook does not automatically implement hotplug switching or saved preferences. [Custom scripts](https://pipewire.pages.freedesktop.org/wireplumber/scripting/custom_scripts.html) explains components and hooks; its current examples are not proof that a proposed script works on 0.5.18.
3. **Host-specific static targets:** configure unique, verified physical node names on the backing streams; use no-fallback plus linger to wait for them. This is simpler and predictable but does not choose another physical device, remember a new choice, or satisfy automatic independent selection. A deliberately enabled fallback changes that tradeoff and may expose audio to an unexpected device.

The selector must explicitly exclude Microphone Proxy, Main Audio, OBS buses, monitor ports and other inappropriate virtual or loopback nodes, and check direction, ports, available routes, profiles and intended device identity. Avoid circular routing; `node.link-group` prevents automatic linking within a group but is not a general graph-cycle or access-control guarantee. A proxy-only priority strategy still needs an explicit policy for saved global defaults and what happens when the user changes them. Do not silently erase saved defaults.

For Scarlett, the existing graph selects its mono Input 1 port; a stereo device target alone does not prove that only channel 1 is used. PipeWire's loopback documentation gives a Scarlett example selecting `FL` with `stream.dont-remix`, then exposing `MONO`, but exact ports and channel positions depend on the active profile. Verify the actual node, channel and levels before relying on it; test both native mono and stereo fallback devices.

## OBS, patchbay and privacy

OBS Track 1 can remain an optional low-priority stereo sink for manually chosen app streams; OBS can capture its monitor, subject to its own configuration. It is not automatically a separate per-app mixer: per-destination levels require suitable gain controls or additional processing. Track 2 is already declared; this research does not recommend removing it. Avoid routing a bus to itself, duplicating desktop capture in OBS, or sending call output back to the call microphone.

Keep qpwgraph nonexclusive for inspection and deliberate manual mixes. Before automatic microphone routing is enabled, reconcile the saved Scarlett -> Microphone Proxy pin: otherwise it can coexist with the automatic feed, causing doubled or unintended audio; the separate Scarlett -> OBS-1 pin is also a direct microphone path and bypasses the proxy. Use one owner per automatic connection and keep sensitive app-to-microphone links temporary unless persistence is intentional. WirePlumber's `node.stream.restore-target` does not restore patchbay links; qpwgraph owns its own saved links. [Settings](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/settings.html), [patchbay manual](https://github.com/rncbc/qpwgraph/blob/main/docs/qpwgraph_patchbay-user_manual.md).

Virtual routing is not a privacy boundary: clients with suitable permissions can access physical devices or monitors directly. Unexpected fallback can send microphone or playback to an unintended endpoint; fail closed where privacy matters, display the active physical target, and inspect live links and mute state. PipeWire enforces per-object permissions supplied by a session manager; application-provided names are not trustworthy security identities. [WirePlumber access policy](https://pipewire.pages.freedesktop.org/wireplumber/policies/client_access.html), [PipeWire properties](https://pipewire.pages.freedesktop.org/pipewire/page_man_pipewire-props_7.html).
